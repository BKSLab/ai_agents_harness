# Состояние задачи через CLI

Эта инструкция нужна при ведении задачи через установленный harness. CLI хранит служебные записи в `HARNESS_HOME` (по умолчанию `~/.agent-harness`), отдельно для ID задачи и корня проекта. Это проверка согласованности и журнал свидетельств, а не самостоятельный источник разрешений пользователя.

Команды выполняет контроллер. Профили implementer и reviewer не имеют Bash; они возвращают изменения, запросы проверок и заключение контроллеру.

Все команды `task` принимают `--project PATH`; без него используют текущий каталог. Выполняя команды из каталога harness вместо целевого проекта, всегда указывай путь явно.

## План

Из целевого проекта:

```text
agent-harness task init fix-refund --project . --title "Исправить возврат" --mode standard
agent-harness task plan fix-refund --input /private/path/plan.yaml
agent-harness task approve fix-refund --reference "Пользователь утвердил этот план в текущей сессии"
```

`approve` вызывай только при реально существующем разрешении. Ссылка описывает его происхождение; команда не заменяет разрешение и не доказывает подлинность введённого текста. Для новой существенной версии плана требуется соответствующее основание.

План принимает JSON или YAML без повторяющихся ключей. Минимальный пример:

```yaml
schema_version: 1
scope:
  - app/refunds.py
  - tests/test_refunds.py
acceptance:
  - id: REQ-1
    description: Повтор возврата не создаёт вторую запись
    checks: [CHECK-1]
risks:
  - id: RISK-1
    description: Повтор после потерянного ответа дублирует возврат
    checks: [CHECK-1]
    severity: high
checks:
  - id: CHECK-1
    argv: ["{python}", "-m", "pytest", "tests/test_refunds.py", "-q"]
    timeout_seconds: 120
```

`scope` — пути файлов или каталогов относительно корня проекта с `/`. Используй реальные пути: пример не предписывает создавать эти файлы. IDs требований, рисков и проверок устойчивы; `checks` связывает их с командами. Команды задаются списком аргументов, не строкой shell. `{python}` выбирает Python окружения проекта. Перед утверждением контроллер проверяет команду и её внешние эффекты; `pytest` сам по себе не гарантирует отсутствие сети или записи.

Для `high-risk` добавь непустые `compatibility` и `rollback`: как проверяется совместимость и как восстановить систему. Текст не заменяет выполненную проверку; необходимые процедуры включи в критерии и проверки. Если обязательную внешнюю проверку выполнить невозможно, запиши ограничение и не объявляй задачу готовой.

## Проверки и ревью

```text
agent-harness task verify fix-refund
agent-harness task snapshot fix-refund
agent-harness task verify fix-refund --snapshot SNAPSHOT_ID
agent-harness task review fix-refund --input /private/path/review.yaml
agent-harness task status fix-refund
```

`SNAPSHOT_ID` бери из результата команды. Передай ревьюеру снимок и созданную контроллером квитанцию, включая fingerprint, `plan_hash` и `verification_id`; их нельзя выдумывать или брать из другой задачи. Формат заключения описан в скиле code-review. Ревью не должно опираться только на HEAD: незакоммиченные изменения входят в предмет проверки. Снимок фиксирует файлы, но не является OS-песочницей.

Когда настроен отдельный вызов модели, контроллер может выполнить `agent-harness review-gate fix-refund --model MODEL_ALIAS`: создать пакет, запустить согласованные проверки и запросить заключение ограниченного reviewer. Это вызов модели с расходом квоты; используемую модель и реальный результат нужно зафиксировать. Обычный `task review` только принимает заключение и сам модель не вызывает.

При продолжении начни с `status`: не сбрасывай журнал и счётчик трёх итераций. Новый код, план или обязательная проверка требуют актуальных свидетельств. Если CLI отсутствует, вести запись можно в принятом журнале, но машинной проверки состояния тогда нет.

## Внешние действия

```text
agent-harness task authorize fix-refund --action push --target origin/main --reference "Пользователь разрешил push в origin/main этого проекта"
agent-harness task check-authorization fix-refund --action push --target origin/main
```

Разрешение на `commit` указывает ветку, на `push` — remote/ветку, на `comment` — ID задачи. Сохранённая цель привязана к фактическому репозиторию. Смена remote, ветки, цели или действия не наследует старое разрешение. Эта команда проверяет запись перед действием; она сама не делает commit, push или отправку комментария. Создание/удаление репозитория и изменение видимости не входят в перечисленные действия и требуют отдельного прямого разрешения.
