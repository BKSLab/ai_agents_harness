# FastAPI — эталонные паттерны архитектуры

Базовые соглашения для нового проекта, не привязанные к конкретной бизнес-логике.
В существующем проекте приоритетны его инструкции, зависимости и архитектура;
локальное исправление не требует их миграции. Примеры с `Item` адаптируй к домену и принятой структуре.

Язык кода, докстрингов, логов и комментариев выбирай по соглашениям проекта; для нового проекта по умолчанию используй русский.

## Стек и версии

Правила ниже написаны под этот стек и предполагают его по умолчанию:

- Python 3.12 (минимум 3.10 — синтаксис `str | None`, `Annotated`).
- FastAPI поверх Starlette, ASGI-сервер Hypercorn/Uvicorn.
- **SQLAlchemy 2.0** в асинхронном режиме: `AsyncSession`, `select()`, `Mapped`/`mapped_column`. Стиль 1.x (`session.query()`, `Column(...)` в теле класса) не применяется.
- **Pydantic v2**: `field_validator`, `model_config = ConfigDict(...)`, `model_validate`. Стиль v1 (`@validator`, `class Config`) не применяется.
- Postgres + asyncpg, Alembic, sqladmin, httpx, pytest + pytest-asyncio + testcontainers.

Сначала проверь версии по зависимостям и коду проекта. `AGENTS.md`/README могут уточнять соглашения, но их отсутствие не означает согласие на смену стека. Между SQLAlchemy 1.x и 2.0, Pydantic v1 и v2 различаются базовые идиомы; не переносись на другую мажорную версию по примеру из скила.

Детали каждого слоя лежат в
`references/` и читаются в момент работы над этим слоем, а не заранее.

## Слоистая архитектура

Строгая однонаправленная цепочка зависимостей:

```
Endpoint → Service → Repository → DB
                 ↘ Client (внешний API / LLM)
```

Правила:
- Эндпоинт не знает о репозитории и о SQLAlchemy. Он знает только сервис.
- Сервис не знает о HTTP (не оперирует `HTTPException`, `status_code` и т.п.) и не пишет SQL. Он оперирует репозиториями, клиентами и доменными исключениями.
- Репозиторий не знает о бизнес-логике. Его методы — это операции с одной таблицей/моделью: `get_*`, `save_*`, `delete_*`, `get_count_*`. Никакой валидации, никаких пересчётов — это работа сервиса.
- Каждый слой бросает **свои** исключения (см. `references/errors.md`). Слой выше перехватывает исключения только нижних слоёв, никогда не "чужие".
- Между сервисами допустима горизонтальная зависимость (один сервис вызывает другой, например `ItemsService` зависит от `OwnersService`), но это всегда явная зависимость через конструктор, а не импорт внутри метода.

## Структура проекта

```
app/
├── main.py                 # FastAPI(), lifespan, роутеры, exception handlers
├── core/                   # settings.py, config_logger.py
├── api/v1/endpoints/       # один файл = один роутер на одну сущность
├── dependencies/           # db_session.py, repositories.py, services.py, clients.py, http_client.py
├── services/               # бизнес-логика, один файл = одна сущность/процесс
├── repositories/           # доступ к БД, один файл = одна модель
├── clients/                # обёртки над внешними API/LLM
├── db/                     # session.py, models/, alembic/
├── schemas/                # Pydantic-схемы запросов/ответов
├── exceptions/             # кастомные исключения, по доменам
├── admin/                  # sqladmin: auth.py + views.py + __init__.py
├── background_tasks/       # периодические задачи
└── utils/                  # точечные утилиты без состояния
```

Полное дерево с комментариями — в `references/project-layout.md`.

Принцип: **один файл — одна сущность**, во всех слоях одновременно. Если в проекте есть сущность
`Item`, у неё есть `db/models/items.py`, `repositories/items.py`, `schemas/items.py`, и обычно часть
`services/items.py`, `api/v1/endpoints/items.py`, `exceptions/items.py`. Это позволяет агенту (и
человеку) находить весь контекст по сущности без grep по всему проекту. Каталог `tests/` зеркалит
эту же структуру.

## Стиль кода и документирования (сквозной)

- Аннотации типов — везде: параметры функций, возвращаемые значения, атрибуты класса. `str | None` вместо `Optional[str]` в новом коде (Python 3.10+), `Annotated[...]` для FastAPI-параметров.
- Докстринги — Google-стиль (`Args:`, `Returns:`, `Raises:`), по-русски, обязательны для всех публичных методов сервисов/репозиториев и для всех эндпоинтов. Для тривиальных приватных методов (одна строка смысла) — однострочный докстринг без секций.
- Комментарии в коде — только там, где не очевидно "почему" (выбор константы, временный compromise, нетривиальное ограничение внешнего API), никогда не пересказывают "что" делает следующая строка.
- Логические блоки внутри большого класса — разделяются комментарием-заголовком (`# Блок ...`), а не пустыми строками без подписи.
- Логи — с эмодзи-префиксом по типу события: 🚀 начало, ✅ успех, ❌ ошибка, ⚠️ обработанное предупреждение, 🔍 запрос к внешнему источнику, 🔄 повтор, 💾 запись в БД, ⚡ конкурентное выполнение, 🤖 LLM. Это осознанный выбор ради быстрого сканирования логов глазами и грепа по эмодзи. Полный словарь и конфигурация логгера — в `references/project-layout.md`.
- Линтер — `ruff` (+ `.flake8` для совместимости), конфигурация лежит в корне проекта и применяется одинаково ко всем слоям без точечных исключений по папкам.
- По умолчанию старый код удаляется, а не оставляется закомментированным — для этого есть история git.

## Правила выбранной архитектуры

Применяй эти ограничения в проекте, который следует описанной архитектуре. В другом проекте оценивай нарушение его собственных контрактов; отличие от примера само по себе не является дефектом:

- Эндпоинт не импортирует репозиторий, `AsyncSession` и SQLAlchemy. Сервис не импортирует `HTTPException` и не оперирует HTTP-статусами.
- `try/except` в эндпоинте перехватывает только **перечисленные** доменные исключения. Голый `except Exception` запрещён — непредусмотренное исключение должно всплыть как 500 со стектрейсом.
- У каждого исключения, способного долететь до эндпоинта, есть `status_code` и `detail`. Конвертация всегда одна: `raise HTTPException(status_code=error.status_code, detail=error.detail)`.
- Репозиторий не отдаёт наружу `SQLAlchemyError`: перехват → `rollback()` → своё `*RepositoryError`. Нарушение уникальности — отдельный `except IntegrityError` и специфичное исключение, а не общий 500.
- Зависимости передаются только через конструктор и Depends-фабрики с алиасами `*Dep`. Ветка «если зависимость не передали — создам сам» запрещена: отсутствие зависимости должно ломать сборку графа, а не тихо менять поведение.
- Долгоживущий обработчик (WebSocket, SSE, streaming) не получает через `Depends` ничего, что удерживает ограниченный ресурс — ни сессию БД, ни HTTP-клиент, ни построенные на них сервисы.
- Каждый эндпоинт полностью описан для OpenAPI: `summary`, `description`, `operation_id` (camelCase), `response_description`, `responses` со всеми реалистичными кодами и примерами, `response_model`, докстринг, пара логов 🚀/✅.
- Каждое поле Pydantic-схемы — `Field(..., description=..., examples=[...])`. Каждое поле ORM-модели — и `doc=`, и `comment=`.
- Логирование — только `%s`-подстановки (`logger.info("...%s", value)`), никогда f-строки. Большие структуры — через `pprint.pformat`.
- Настройки читаются только через `get_settings()` с `@lru_cache`. Ресурсные лимиты (размеры пулов, таймауты, retry, семафоры) задаются явно в `Settings`, а не литералами по коду и не умолчаниями библиотек.
- Alembic выполняет только DDL. `INSERT`/`UPDATE`/`DELETE`/backfill в миграциях запрещены — для этого идемпотентные seed-скрипты и отдельные operational-команды.
- Репозиторий тестируется на реальном Postgres (`testcontainers`), а не на моках сессии. `AsyncMock` — всегда со `spec=`.
- Ни одна связь ORM не загружается лениво: стратегия задаётся явно в запросе репозитория, а `lazy="raise_on_sql"` в модели превращает забытую загрузку в явную ошибку вместо N+1 или падения при сериализации ответа.
- В `async def` не выполняется ничего блокирующего: синхронные драйверы БД, `requests`, `time.sleep`, синхронные SDK, чтение больших файлов останавливают весь воркер, а не один запрос.
- Каждый фильтр репозитория опирается на индекс, а способ пагинации (offset или keyset) выбирается по размеру данных, а не по привычке.
- Архитектурные ограничения из этого списка проверяются тестом, а не договорённостью (см. `references/testing.md`).

## Порядок работы над новой сущностью

Сквозной проход снизу вверх — каждый шаг опирается на предыдущий:

1. `db/models/items.py` — ORM-модель (`doc=`/`comment=` на каждом поле, `__repr__`, constraints).
2. Миграция Alembic — одно концептуальное изменение, только DDL.
3. `exceptions/items.py` — доменные исключения со `status_code` и `detail`.
4. `repositories/items.py` — методы-запросы, обработка ошибок БД.
5. `schemas/items.py` — схемы запроса и ответа.
6. `services/items.py` — use-case'ы, зависимости через конструктор.
7. `dependencies/repositories.py` и `dependencies/services.py` — фабрики и алиасы `*Dep`.
8. `api/v1/endpoints/items.py` + `include_router(..., prefix="/api/v1")` в `main.py`.
9. `admin/views.py` — `ModelView`, если сущность нужна в админке.
10. Тесты: `tests/unit/services/`, `tests/integration/repositories/`, `tests/api/endpoints/`.

Если задача касается только одного слоя — берётся только его шаг, но правила соседних слоёв
из «Правил выбранной архитектуры» продолжают действовать.
