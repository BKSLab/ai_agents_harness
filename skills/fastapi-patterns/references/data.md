# Репозитории, модели, миграции, админка

> Часть скилла `fastapi-patterns`. Читать при работе со слоем данных:
> новый репозиторий или метод, ORM-модель, транзакция, миграция, sqladmin.

---

## Репозитории

- Один репозиторий = одна модель/таблица (изредка — тесно связанная пара таблиц).
- Конструктор принимает `db_session: AsyncSession`, хранит как `self.db_session`.
- Каждый публичный метод — это один SQL-запрос (через SQLAlchemy Core/ORM `select`/`insert`/`update`/`delete`), оборачивается в `try/except (SQLAlchemyError, Exception)`, при ошибке — `rollback()` и `raise СвоёRepositoryError(...) from error`.
- Чтение не делает `commit()`. Простая самостоятельная запись по умолчанию делает `commit()` после `execute()`. Метод, участвующий в составном use-case, принимает явный keyword-only `commit: bool = True`: при `False` выполняет `flush()`, а единственный финальный `commit()` делает сервис-владелец операции. `rollback()` в `except` обязателен в обоих режимах.
- Массовая вставка — батчами (`SAVE_BATCH_SIZE` как константа класса), с логированием прогресса по батчам и индивидуальной обработкой ошибки конкретного батча, чтобы в логе было видно, какой именно батч сломался.
- Фильтрация — собирается через последовательные `stmt = stmt.where(...)` по присутствующим опциональным параметрам, а не через построение строки SQL.
- Методы подсчёта (`get_count_*`) — отдельные от методов получения данных (`get_*`), даже если фильтры идентичны, чтобы можно было получить total для пагинации без выгрузки самих строк.
- Аномалии данных, которые не являются ошибкой, но достойны внимания (например, найдено более одной записи там, где ожидалась одна) — логируются `logger.warning`, не превращаются в исключение, если есть разумный способ продолжить (взять первую запись).

### Логирование в репозитории

- Репозиторий логирует факты работы с данными, а не сам SQL: 💾 сохранение, ➕/🗑️ добавление и удаление, 📋 получение списка — с ключом записи и числом затронутых строк.
- Ошибка БД логируется здесь через `logger.error(..., exc_info=True)` перед тем, как обернуться в `*RepositoryError`. Полный traceback пишет эндпоинт (скилл `fastapi-endpoints`).
- Содержимое строк не выгружается в лог целиком: пишутся ключи и количества. Иначе лог превращается в копию таблицы и утаскивает туда персональные данные.

### Загрузка связей и N+1

- Стратегия загрузки связей задаётся **явно в запросе репозитория** — `selectinload(...)` для коллекций, `joinedload(...)` для связи «к одному», — а не оставляется на умолчание ORM. Метод репозитория обязан вернуть объект, полностью пригодный для того, что с ним будет делать вызывающий код: ни сервис, ни схема ответа не должны догружать ничего сами.
- Все `relationship` объявляются с `lazy="raise_on_sql"`. Это переводит забытую загрузку из тихой деградации в явную ошибку в момент разработки. Без этого промах проявляется либо как N+1 (список из 50 записей — 51 запрос, при этом всё работает и все тесты зелёные), либо как `MissingGreenlet` при сериализации ответа — то есть падение уже за пределами репозитория, там, где причину искать никто не будет.
- `async_sessionmaker(..., expire_on_commit=False)`. По умолчанию после `commit()` все атрибуты объектов помечаются протухшими, и первое же обращение к любому из них — включая обращение из Pydantic-схемы ответа — уходит в неявный запрос к БД за пределами метода репозитория.
- `selectinload` против `joinedload`: `selectinload` делает отдельный запрос `IN (...)` и не размножает строки — выбор по умолчанию для коллекций. `joinedload` уместен для связи «к одному», где джойн не увеличивает число строк; джойн коллекции через него даёт декартово произведение и вычитывает родительские поля столько раз, сколько дочерних записей.
- Как выглядит нарушение в проде: время ответа эндпоинта растёт линейно от размера страницы, а не от факта запроса; в логе БД — пачки одинаковых по форме запросов, различающихся только значением id; число запросов к БД на один HTTP-запрос равно числу элементов в ответе. На тестовых данных в пять записей это неотличимо от нормы, поэтому ловится либо `lazy="raise_on_sql"`, либо тестом со счётчиком запросов.

### Индексы под запросы

- Каждый фильтр, по которому репозиторий реально ищет, опирается на индекс. Индекс — часть модели (`index=True` или `Index(...)` в `__table_args__`) и появляется в той же миграции, что и запрос, которому он нужен, а не после первой жалобы на медленный список.
- Составной индекс строится в порядке использования в запросе: индекс по `(owner_id, created_at)` обслуживает фильтр по владельцу вместе с сортировкой по дате, обратный порядок — нет.
- Регистронезависимый поиск подстроки (`ilike '%...%'`) обычным B-tree индексом не обслуживается в принципе. Варианты — `pg_trgm` с GIN-индексом, поиск по префиксу или полнотекстовый поиск; «добавим `index=True`, станет быстрее» здесь не работает.
- Фильтрация по полям внутри `JSONB` требует GIN-индекса. Если по такому полю приходится фильтровать регулярно — это сигнал, что поле пора вынести в обычную колонку.
- Частичный индекс (`postgresql_where=...`) — правильный ответ там, где запрос всегда ходит по узкому подмножеству (активные записи, необработанные события): он меньше, быстрее и меньше мешает записи.

### Пагинация: offset или keyset

Схема ответа со `total`/`page`/`page_size` едина для всех списков проекта (скилл `fastapi-endpoints`), но способ выборки под ней — это выбор, а не умолчание:

- **Offset** (`.offset().limit()` плюс отдельный `get_count_*`) — для админки, справочников и заведомо небольших выборок. Стоимость `OFFSET n` линейна по `n`: БД читает и отбрасывает все пропущенные строки. Отдельно платится за `COUNT(*)`, который на большой таблице выполняется полным проходом при запросе **каждой** страницы.
- **Keyset** (`WHERE (created_at, id) < (:last_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT :size`) — для больших и растущих таблиц и для бесконечной прокрутки. Стоимость не зависит от глубины страницы, и результат не «съезжает», когда между запросами страниц кто-то вставил новую запись.
- Если `total` нужен интерфейсу, но точность не критична, оценка (`pg_class.reltuples`) или счёт с потолком («более 1000») честнее и дешевле точного `COUNT(*)` на каждый запрос.

### Транзакционная граница составного use-case

- Владелец транзакции — application service, который принимает бизнес-решение. Endpoint и вложенные repository/service не должны создавать скрытые промежуточные commit.
- Все изменения одной БД-сессии, относящиеся к одному факту, фиксируются вместе: бизнес-модель, `case_events`, notification и `domain_events`/outbox.
- Вложенный сервис получает явный `commit=False`; не использовать неявные флаги в payload или проверку типа вызывающего кода.
- Для операции с внешней очередью минимально допустима двухфазная схема: `(1) persist preparing + event, commit; (2) publish; (3) persist queue result + event, commit`. Publish до первого commit запрещён.
- Полная гарантия доставки требует transactional outbox worker с retry. DB-транзакцию нельзя держать открытой во время сетевого publish и считать это атомарностью.
- Callback внешней системы обязан быть идемпотентным: финальный статус монотонен, событие имеет `idempotency_key`, а повтор не создаёт notification и journal event.

### Журнал кейса (`case_events`)

- `CaseEventService` — обязательная constructor dependency для сервисов, владеющих журналируемыми действиями. Ветка `if case_event_service` в таком сервисе запрещена: отсутствие зависимости должно обнаруживаться при сборке DI.
- Событие строится до финального commit и сохраняется в одной транзакции с бизнес-изменением. `record()`/`build_event()` не коммитят самостоятельно.
- `kind` описывает состоявшийся факт, а не намерение: `case_closed` не заменяется `case_resolved`, rejected transition не записывается как успешный `status_changed`, ошибка очереди не называется `reply_queued`.
- Для ручного HTTP-действия `actor_id` и `actor_name` берутся только из `CurrentUser`, а не из тела запроса. Для worker/consumer используются стабильные system/agent identifiers.
- В каждом событии заполняются применимые provenance-поля: `actor_type`, `source`, `operation_id`, `causation_id`, `idempotency_key`, `schema_version`. `comment` предназначен для человекочитаемого текста, структурные данные находятся в `payload`.
- Timeline сортируется по `(at, recorded_at, id)`. `at` — бизнес-время факта, `recorded_at` — время записи приложением.
- Обычные сообщения и emoji reactions внутреннего discussion не дублируются в timeline. Журналируются бизнес-значимые действия вокруг discussion: участники, запрос/ответ агента и ошибки workflow.
- Для ответа с помощью LLM каждое пользовательское или внешнее действие создаёт отдельное событие и не копирует payload соседних этапов: `reply_preparation_requested` хранит запрос менеджера и коммитится до вызова LLM; `reply_draft_generated` хранит результат LLM; `message_out` хранит финальный текст при нажатии «Ответить». Последующие `outbound_*`/`reply_queued`/`reply_sent`/`reply_failed` содержат только статусы доставки. Вся цепочка связывается server-generated `operation_id`; browser не формирует actor и не считается источником delivery-факта.
- LLM не называется доменным агентом. Actor события подготовки — инициировавший действие пользователь, `source` указывает use case, а происхождение результата явно отражается в `kind`, `comment` и payload.

## Модели SQLAlchemy

```python
from datetime import datetime
from typing import Optional

from sqlalchemy import DateTime, ForeignKey, String, Text, UniqueConstraint, func
from sqlalchemy.orm import Mapped, mapped_column

from .base import Base


class Item(Base):
    """Модель для хранения сущности Item."""

    __tablename__ = 'items'

    __table_args__ = (
        UniqueConstraint('external_id', 'owner_id', name='unique_items_external_id__owner_id'),
    )

    id: Mapped[int] = mapped_column(
        primary_key=True,
        comment='Уникальный идентификатор записи.',
    )
    external_id: Mapped[str] = mapped_column(
        String(length=300),
        nullable=False,
        doc='Идентификатор сущности во внешней системе.',
        comment='ID записи на стороне источника данных.',
    )
    owner_id: Mapped[int] = mapped_column(
        ForeignKey('owners.id', ondelete='CASCADE'),
        nullable=False,
        doc='Владелец записи.',
        comment='Внешний ключ на таблицу owners. При удалении владельца запись удаляется.',
    )
    title: Mapped[str] = mapped_column(
        Text,
        nullable=False,
        doc='Название сущности.',
        comment='Человекочитаемое название записи.',
    )
    description: Mapped[Optional[str]] = mapped_column(
        Text,
        nullable=True,
        doc='Описание сущности.',
        comment='Произвольное текстовое описание, может отсутствовать.',
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
        onupdate=func.now(),
        nullable=False,
        doc='Дата последнего обновления записи.',
        comment='Метка времени последнего изменения записи, обновляется автоматически на стороне БД.',
    )

    def __repr__(self) -> str:
        return f"<Item(id={self.id}, external_id='{self.external_id}', title='{self.title}')>"
```

Ключевые моменты этого примера:
- **Каждое поле документировано дважды** — `doc=` для разработчика/IDE, `comment=` для самой БД (виден в любом SQL-клиенте независимо от кода).
- `__table_args__` с `UniqueConstraint` и явным `name=`, когда уникальность составная (а не на одном поле).
- `ForeignKey(..., ondelete='CASCADE')` — каскад описан на уровне схемы БД, не оставлен только на совести кода приложения.
- `onupdate=func.now()` для `updated_at` — обновление метки времени на стороне БД при каждом `UPDATE`, без ручного выставления в Python-коде.
- `__repr__` — id плюс 1–2 ключевых поля, достаточно для логов и отладки, не весь объект целиком.

Дальше — наследование от единой `Base(DeclarativeBase)` (плюс промежуточные абстрактные модели для общих наборов полей у родственных таблиц, например общая базовая модель для записей, поступающих из разных внешних источников с одинаковой структурой).
- Имя класса — PascalCase в единственном или множественном числе по смыслу сущности; `__tablename__` — snake_case, множественное число.
- Документирование **каждого** поля двумя независимыми способами:
  - `doc=` — для разработчика, видно через `__doc__`/IDE/автогенерацию.
  - `comment=` — для самой БД, видно в любом SQL-клиенте (DBeaver, psql `\d+`), не зависит от того, открыт ли код проекта.
- У каждой модели — `__repr__`, возвращающий компактное и информативное представление (id + 1-2 ключевых поля), для удобной отладки и логов.
- Уникальность на уровне домена — через `UniqueConstraint` с явным `name=`, а не только через `unique=True` на одном поле, если уникальность составная.
- Внешние ключи — с явным `ondelete=` (как правило `CASCADE` для зависимых сущностей), чтобы целостность данных не держалась только на коде приложения.
- Поля времени (`created_at`/`updated_at`) — `DateTime(timezone=True)`, `server_default=func.now()`, генерируются на стороне БД, а не в Python-коде, чтобы избежать рассинхронизации времени между инстансами приложения.
- Общие наборы полей у родственных сущностей (например, записи из разных внешних источников с одинаковой структурой) — выносятся в абстрактную базовую модель: `__abstract__ = True`, без `__tablename__`. Конкретные модели наследуются от неё и добавляют только то, что у них специфично (например, `updated_at` и `UniqueConstraint` только там, где это нужно). Это устраняет дублирование колонок без создания лишней таблицы.
- Таблицы-журналы событий (аналитика, аудит: "событие поиска", "сессия обработки", "событие изменения статуса") — отдельный, более простой тип модели: только `id`, `created_at` и набор полей-снимков на момент события. У них нет `updated_at` (запись неизменяема после создания), обычно не используется `doc=` (это не доменная сущность, которую разработчик долго изучает, а лог), а описание полей в `comment=` короче и фокусируется на "что значит это число/флаг" для аналитики. У репозитория такой модели нет методов `update_*`/`delete_*` — только `save_event`/`get_*` для агрегатов.
- Гибкие, не вполне табличные данные (произвольная структура ответа, список вопросов/ответов анкеты) — `JSONB`, а не отдельная связанная таблица, если данные всегда читаются целиком вместе с родительской записью и не требуют отдельных запросов/фильтрации по внутренним полям.

## Админка (sqladmin)

- `admin/__init__.py` — единая фабрика `create_admin(app, engine) -> Admin`, вызывается один раз из `main.py`. Здесь и только здесь собираются все `ModelView`/`BaseView`.
- `admin/auth.py` — `AuthenticationBackend` на логине и пароле из настроек (`admin_login`/`admin_password` как `SecretStr`), хранение факта входа в `request.session`. Никогда не использовать единый сервисный API-ключ как пароль в админку — это разные плоскости доступа с разным жизненным циклом.
- `admin/views.py` — каждая сущность представлена `ModelView`, со связкой:
  - `name`/`name_plural`/`icon` (FontAwesome) — обязательны, для визуальной узнаваемости разделов.
  - `column_list`/`column_searchable_list`/`column_sortable_list`/`column_default_sort` — явно перечислены, не оставлены на дефолт "все поля".
  - `column_formatters`/`column_formatters_detail` — кастомные рендеры (цветные бейджи статусов, pretty-print JSON, обрезка длинного текста) через небольшие функции `_fmt_*(model, attr) -> Markup`, переиспользуемые между списком и детальной страницей.
  - `can_create`/`can_edit`/`can_delete` — выставлены осознанно для каждой сущности по тому, что должно быть редактируемо человеком, а что — только просматриваемая система записей (логи событий, истории).
- Кастомные страницы, не привязанные к одной модели (агрегированная статистика, кастомные отчёты) — через `BaseView` + `@expose`, с собственным шаблоном Jinja, открывающие собственную короткую `AsyncSession` поверх переданного `engine` (а не через основной DI, потому что admin живёт вне обычного цикла запрос/Depends).
- Визуальный стиль админки соответствует общему дизайн-гайду проекта (тёмная тема, акцентный цвет для статусов/бейджей) — админка не выглядит как "техническая заглушка", а как часть продукта.

## Миграции (Alembic)

- Имя файла миграции — `<дата>_<время>_<смысловое_описание>.py`, чтобы порядок и смысл были видны прямо в списке файлов без открытия содержимого.
- Одна миграция — одно концептуальное изменение (добавить таблицу / добавить поле / изменить constraint), не "накопить и сделать одним махом" — так проще откатывать точечно.
- `env.py` Alembic собирает `target_metadata` из той же `Base`, что и приложение — миграции и модели не могут разойтись по структуре без явного `autogenerate diff`.
- Alembic выполняет только DDL: таблицы, колонки, индексы, внешние ключи и constraints. В migration-файлах запрещены `INSERT`, `UPDATE`, `DELETE`, `bulk_insert`, начальные бизнес-настройки и backfill данных.
- Базовые данные и настройки загружаются отдельными идемпотентными seed-скриптами после `alembic upgrade head`. Повторный запуск seed добавляет отсутствующее, но не перетирает ручную конфигурацию и не меняет lifecycle деактивированных сущностей.
- Если изменение схемы требует преобразования существующих данных, оно оформляется отдельной явно запускаемой operational-командой с собственными проверками и планом отката, а не скрывается внутри Alembic.
