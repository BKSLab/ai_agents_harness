# AI Agents Harness

Harness 0.4.0 для Kimi Code, Claude Code и Codex: 16 скилов, общий клиент Bitrix24, установка и диагностика, сохранение состояния задачи, проверок и независимого ревью. Контроллер запускает согласованные проверки и записывает результат; исполнитель меняет код, а ревьюер проверяет отдельный снимок.

Рабочий репозиторий — закрытый BKSLab/ai_agents_harness. Обновления отправляются в него; установка и обновление не создают других репозиториев и не меняют видимость.

Текущая версия содержит общие инструкции и код. Адрес портала, учётные данные, люди, чаты, журналы и резервные копии хранятся на рабочей машине вне текущих файлов Git. Исходная история с внутренними данными сохранена в закрытом репозитории.

## Установка

Требуются Git и Python 3.11+. Первый запуск загружает зависимости установщика в локальную .venv; инструменты Bitrix используют только стандартную библиотеку Python.

```bash
git clone https://github.com/BKSLab/ai_agents_harness.git
cd ai_agents_harness
python install.py --agents kimi claude codex --components skills instructions hooks agents --dry-run
python install.py --agents kimi claude codex --components skills instructions hooks agents
```

Выбирай нужных агентов и компоненты. Без `--components` устанавливаются только скилы, как в предыдущих версиях. Хуки и ограниченные профили поддерживаются для Kimi; для Claude/Codex эти компоненты отмечаются как `unsupported`. Также доступны install.ps1 и install.sh с теми же аргументами. Явный выбор агента создаёт его каталог; без выбора установщик находит существующие каталоги и сообщает ошибку, если не нашёл ни одного.

Для следующих команд используй Python из созданной .venv:

| ОС | Интерпретатор |
|---|---|
| Windows | .venv/Scripts/python.exe |
| Linux/macOS | .venv/bin/python |

В примерах ниже venv активирована.

## Подключение и обновление

| Агент | Подключение | Проверка в интерфейсе |
|---|---|---|
| Kimi Code | extra_skill_dirs в config.toml указывает на skills/ репозитория | /skill: |
| Claude Code | управляемые копии в ~/.claude/skills | /skills или /имя-скила |
| Codex | управляемые копии в ~/.agents/skills | /skills или $имя-скила |

Компонент `instructions` добавляет управляемый блок из `global/AGENTS.md` в `~/.kimi-code/AGENTS.md`, `~/.claude/CLAUDE.md` и `~/.codex/AGENTS.md`. Текст пользователя вне блока сохраняется. `hooks` объединяет записи `[[hooks]]` Kimi, `agents` регистрирует каталог `agents/` через `extra_agent_dirs`. Настройки модели и авторизации установщик не заменяет.

KIMI_CODE_HOME и CLAUDE_CONFIG_DIR переопределяют соответствующие каталоги. CODEX_HOME задаёт каталог глобальных инструкций Codex и учитывается при миграции старых копий; общий пользовательский каталог скилов Codex — ~/.agents/skills.

Kimi также читает ~/.agents/skills с более высоким приоритетом, чем extra_skill_dirs. При совместной установке с Codex обновляй все установленные цели одной командой, чтобы Kimi не использовал старую общую копию.

```bash
git pull
python manage.py install --agents kimi claude codex --components skills instructions hooks agents --dry-run
python manage.py install --agents kimi claude codex --components skills instructions hooks agents
python manage.py doctor
```

Установщик дополняет TOML без потери остальных настроек и комментариев. Повторный запуск без изменений ничего не переписывает. Перенос репозитория обновляет ранее зарегистрированный путь Kimi, сохраняя сторонние каталоги.

Установщик ведёт отдельные квитанции в ~/.agent-harness/installations. Он удаляет устаревшие файлы только из своего прошлого списка. Пользовательские правки и коллизии останавливают установку до изменений. После просмотра плана можно использовать --replace-conflicts: исходные файлы сохраняются в ~/.agent-harness/backups вместе с restore.json. При ошибке применения выполненные изменения откатываются.

Для миграции старой установки добавь --migrate-legacy-codex: удаляются только старые копии, совпадающие с файлами текущего Git HEAD с учётом преобразования LF/CRLF. Запускай миграцию до коммита обновления. Изменённые старые копии требуют ручного разбора. Системные скилы Codex не затрагиваются.

После изменения конфигурации перезапусти агента. Команда doctor проверяет файлы и регистрацию, но не доказывает, что уже запущенная сессия перечитала скилы.

## Цикл разработки и состояние задачи

`dev-pipeline` ведёт задачу через требования, риски, план, реализацию, проверки и ревью. `risk-assessment` связывает требования и риски с проверками. `code-review` ищет подтверждённые дефекты и выдаёт `approved`, `changes_requested` или `blocked`. Разовое ревью доступного diff возможно и без формального плана, с явным указанием пределов проверки.

| Режим | Применение | Условие готовности управляемой задачи |
|---|---|---|
| `light` | Небольшая локальная правка | План и актуальные обязательные проверки |
| `standard` | Баг или фича с изменением поведения | Проверки и независимое ревью текущего снимка |
| `high-risk` | Данные, миграции, доступ, внешние контракты | Всё из standard, плюс планы совместимости и восстановления |

Явно выбранный пользователем полный цикл не сокращается. Уже согласованный план и разрешение реализовать его не требуют повторного подтверждения. Существенное изменение цели или внешнего действия требует соответствующего разрешения; «продолжай» сохраняет прежний объём.

Служебные записи лежат в `HARNESS_HOME`, по умолчанию `~/.agent-harness`: SQLite, контрольные записи состояния и результаты команд — в `tasks/`, новые снимки — в `snapshots/`. Плоское расположение снимков сокращает пути для Windows Git; при слишком длинном пути CLI предложит более короткий `HARNESS_HOME`. Настройки Git пользователя не меняются. Ранее созданные снимки продолжают использовать сохранённые пути. Задача привязана к ID и корню проекта. После перезапуска `task status` показывает этап, `ready`, блокирующие причины, следующий шаг, число попыток модели и актуальные свидетельства. Журнал `docs/tasks/` автоматически не создаётся; `--journal` только запоминает уже принятое проектом расположение.

`task init` и `task use ID` выбирают активную задачу проекта для Git-гейта. После выхода из управляемого процесса вызови `task release ID --reference "Причина выхода"`: история сохраняется, готовность и отправка кода этим не подтверждаются. Для продолжения снова используй `task use ID`.

### Начать задачу

Команда `agent-harness` доступна в активированной venv harness. Ниже примеры выполняются из корня целевого Git-проекта. Любая команда `task` принимает `--project PATH`; без него используется текущий каталог.

```text
agent-harness task init fix-refund --title "Исправить повтор возврата" --mode standard
agent-harness task plan fix-refund --input /private/path/plan.yaml
agent-harness task status fix-refund
```

`plan.yaml` — UTF-8 YAML или JSON. Используй реальные пути и команды проекта; этот пример не требует создавать названные файлы:

```yaml
schema_version: 1
scope: [app/refunds.py, tests/test_refunds.py]
acceptance:
  - id: REQ-1
    description: Повтор возврата не создаёт вторую запись
    checks: [CHECK-1]
risks:
  - id: RISK-1
    description: Потерянный ответ приводит к повторной внешней записи
    severity: high
    checks: [CHECK-1]
checks:
  - id: CHECK-1
    argv: ["{python}", "-m", "pytest", "tests/test_refunds.py", "-q"]
    timeout_seconds: 120
```

Каждый критерий и риск ссылаются на существующую проверку. `scope` содержит относительные пути с `/`. Команда — список аргументов; `{python}` выбирает Python из `.venv` целевого проекта, при её отсутствии — интерпретатор контроллера. Для `high-risk` обязательны также непустые `compatibility` и `rollback`. Схемы и подробности: [task-state.md](skills/dev-pipeline/references/task-state.md), [task_schemas.py](harness_cli/task_schemas.py).

До запуска проверок контроллер фиксирует **реальное** одобрение этой версии плана:

```text
agent-harness task approve fix-refund --reference "Ссылка на фактическое сообщение пользователя об одобрении"
```

`--reference` — происхождение разрешения, а не возможность выдать его себе. Команда не проверяет подлинность сообщения. Поручение выполнить уже согласованный план можно записать без нового вопроса; текст ссылки нельзя выдумывать. Изменение плана сбрасывает его одобрение и разрешения на отправку.

Чужие незакоммиченные файлы не должны становиться скрытыми входами проверки. Для управляемого цикла с такими файлами используй отдельный checkout. `--adopt-changes` при инициализации применим только к существующим правкам, которые явно относятся к порученной задаче; это не способ присвоить чужие изменения. Секретные файлы должны находиться вне репозитория и входов снимка.

Сверка Git допускает нормализацию LF/CRLF, но отклоняет `filter`, `ident` и `working-tree-encoding`: они могут менять проверенное содержимое при добавлении в Git. Такие проекты требуют отдельной проверки отправляемого представления. Хеши рассчитываются одним процессом Git; внутренняя проверка ограничена шестью секундами и при исчерпании бюджета возвращает отказ до десятисекундного таймаута хука.

### Проверить и получить независимое заключение

```text
agent-harness task verify fix-refund
agent-harness models
agent-harness review-gate fix-refund --model MODEL_ALIAS
agent-harness task status fix-refund
```

`models` показывает настроенные в Kimi псевдонимы моделей без учётных данных. `review-gate` требует явный `--model`: подмена другой моделью при ошибке не выполняется. Вызов расходует квоту выбранной модели.

Контроллер проверяет рабочую копию, создаёт отдельный снимок и выполняет команды плана на нём. Ревьюер получает исходную задачу, план, diff, снимок и квитанцию контроллера. Схема заключения включает fingerprint файлов, `plan_hash`, `snapshot_id`, `verification_id`, устойчивые ID замечаний, доказательства и ограничения. Старый отчёт или текст автора «тесты зелёные» не подходят. Изменение кода делает прежнее свидетельство недостаточным; недоступная обязательная проверка не считается успешной.

Ревью и попытки вызова модели ограничены тремя проходами на план; повторение одного спора без прогресса видно в состоянии. Не меняй план формально, чтобы обнулить лимит. При прерванной проверке `task recover ID --reference "Причина и подтверждение остановки прежнего запуска"` позволяет снять запись активного запуска только после выяснения его состояния; команда не останавливает живой процесс.

Без автоматического вызова модели доступны `task snapshot`, `task verify --snapshot SNAPSHOT_ID` и `task review --input FILE`. Контроллер передаёт независимому ревьюеру реальные квитанции; формат — [verdict.md](skills/code-review/references/verdict.md). Ручная загрузка заключения не удостоверяет личность или независимость автора.

### Зафиксировать и отправить

Готовность и разрешение — разные условия. `task authorize` записывает конкретное уже полученное разрешение на `commit`, `push` или `comment`; команда сама ничего не отправляет. Репозиторий, адрес remote, ветка и версия плана входят в границы записи.

```text
agent-harness task authorize fix-refund --action commit --target main --reference "Фактическое разрешение пользователя на коммит"
agent-harness task authorize fix-refund --action push --target origin/main --reference "Фактическое разрешение пользователя на push в origin/main"
agent-harness task check-authorization fix-refund --action push --target origin/main
```

Kimi-хук `git_gate` проверяет активную задачу перед распознанными Git-командами. Для коммита содержимое Git index должно соответствовать проверенному дереву, для push — содержимое отправляемого HEAD. Зелёная рабочая копия не разрешает отправить другой staged-файл или старый коммит. Remote и refspec указываются явно, например `git push origin HEAD:refs/heads/main`; общий `git push`, force-push, неоднозначные shell-цепочки и отправка непроверенной ветки не проходят управляемый путь.

Смену репозитория или его видимости эти разрешения не покрывают. Комментарий в Битриксе требует своего разрешения с ID задачи и проверки перед отправкой. Проверка разрешений — кооперативный механизм контроллера, а не перехват всех процессов ОС; прямой вызов вне интеграции может её обойти.

## Роли и хуки Kimi

| Профиль | Инструменты | Результат |
|---|---|---|
| `implementer` | Read, Grep, Glob, Write, Edit | Изменения в назначенных файлах и запросы проверок контроллеру |
| `reviewer` | Read, Grep, Glob | Независимое заключение по снимку и квитанции контроллера |

В обоих профилях отсутствуют Bash, делегирование и MCP-инструменты. Команды, Git и внешние записи выполняет контроллер в рамках разрешений. Список инструментов не ограничивает доступные файлы на уровне ОС: для строгой изоляции нужны отдельное окружение и права. Снимок также не является sandbox; согласованные тесты могут обращаться к сети и окружающей файловой системе.

`protect_secrets` распознаёт прямые чтения/отправку файлов с известными секретными именами, разрешая `.env.example`. `lint_on_edit` выбирает Ruff окружения проекта и возвращает `passed / failed / skipped / error`; отсутствие Ruff или ошибка конфигурации видны. `git_gate` проверяет готовность и цель для распознанных commit/push управляемой задачи. Для проектов без активной задачи он не вводит новый процесс.

Хуки Kimi имеют семантику fail-open: ошибка или таймаут обработчика не гарантируют запрет действия. Регулярные выражения, разбор буквальных shell-команд и инструкции ролей дают дополнительные барьеры, но не обеспечивают изоляцию произвольного кода. Установка управляется компонентом `hooks`; фрагмент для ручной настройки — [hooks.toml](config/kimi/hooks.toml). Официальные контракты: [хуки Kimi](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/hooks.html), [профили агентов Kimi](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/agents.html).

## Частная конфигурация Bitrix

Задай вне репозитория:

- BITRIX_PORTAL_URL — HTTPS-адрес портала без пути.
- BITRIX_WEBHOOK_USER_ID — ID владельца входящего вебхука.
- BITRIX_WEBHOOK_TOKEN — только секретная часть вебхука.
- BITRIX_CA_BUNDLE — при необходимости путь к доверенному корпоративному CA в PEM.
- BITRIX_TIMEOUT_SECONDS — таймаут запроса, по умолчанию 20 секунд.
- BITRIX_READ_RETRIES — количество повторов чтения, по умолчанию 2, максимум 3.

Используй менеджер секретов или пользовательские переменные окружения ОС. Не вставляй значения в команды, переписку, отчёты или Git. Файл .env.example содержит только имена; автоматической загрузки .env нет. После изменения окружения уже запущенное приложение нужно полностью перезапустить.

Скопируй config/profile.example.json в ~/.agent-harness/profile.json и заполни локальные ID и псевдонимы. BITRIX_PROFILE задаёт другой путь. HARNESS_HOME меняет каталог профиля, квитанций, журнала и резервных копий. Адрес портала и токен в профиль не записываются. Каталог должен быть доступен только его владельцу.

Старый BITRIX_WEBHOOK поддерживается временно. При заданных новых переменных используются они. После перевода всех потребителей удаляй старую переменную самостоятельно. Если токен уже оказался в переписке или файлах, создай новый вебхук в Bitrix, обнови окружение и отзови старый. Перенос значения между переменными не является ротацией.

## Вызовы инструментов

Чтение:

```bash
python skills/bitrix-list-tasks/scripts/list_tasks.py creator active
python skills/bitrix-get-task/scripts/get_task.py 42
```

Для записи сформируй UTF-8 JSON-файл. Например, сообщение: {"text":"Текст с BBCode"}. Создай UUID для логического действия и передай его через --operation-id. При повторе используй тот же UUID:

```bash
python skills/bitrix-send-chat-message/scripts/send_message.py operations --input message.json --operation-id action-unique-uuid
```

Сложный текст передавай файлом или stdin, не подставляй его в shell-команду. Вывод — единый JSON: ok/data/meta либо ok/error. Адрес портала и токен маскируются, ссылки возвращаются относительными путями. HTTP 200 сам по себе не означает успех: проверяется ожидаемый результат конкретного метода.

Запись не повторяется автоматически. Локальный SQLite-журнал предотвращает повтор одной операции с тем же ID и останавливает вызовы после неопределённого исхода. Это защита в пределах одного HARNESS_HOME, а не гарантия между разными машинами. Журнал не хранит тексты сообщений или токены.

```bash
python manage.py operations
```

Полный контракт: [skills/_shared/CONTRACT.md](skills/_shared/CONTRACT.md).

## Диагностика и проверки

```bash
python manage.py doctor
python manage.py capabilities
python manage.py doctor --no-probes
python manage.py check
python manage.py check --history
python -m pip install -e ".[dev]"
python -m pytest -q
python -m ruff check .
```

`doctor` показывает версии, регистрацию, расхождения копий и наличие конфигурации без её значений. `capabilities` раскладывает каждую возможность на поддержку, наличие файлов, настройку, принадлежность установщику и результат пробы. Видны различия `missing`, `drift`, `unsupported`, `configured`, `error`; регистрация не подменяется утверждением «проверено».

При настроенных хуках запускаются только собственные скрипты harness с синтетическим JSON, в отдельном временном каталоге. Shell-команды из JSON не исполняются; запросов в Bitrix и вызовов модели нет. Проба не доказывает, что конкретная живая сессия Kimi вызвала хук; `--no-probes` отключает эти прогоны. Ненулевой код doctor означает проблему или неполную настройку, включая отсутствие нужного окружения Bitrix.

check проверяет YAML, имена и ссылки скилов, allowlist профилей, ссылки хуков, компиляцию, известные форматы секретов и адреса клиентских порталов. --history просматривает все доступные Git refs. Локальный ~/.agent-harness/publication-denylist.json позволяет добавить частные строки; в отчёт попадают только расположение и правило. Проверка известных шаблонов не доказывает отсутствие всех возможных секретов.

GitHub Actions запускает проверки на Windows, Linux и macOS с Python 3.11 и 3.13. В CI проверяются текущие файлы; аудит всей сохранённой истории запускается отдельно через check --history и может обнаруживать внутренние данные старых коммитов. Тесты используют временные каталоги и подставные API, не рабочий портал.

## Проверка решений модели

В evals/scenarios.json находятся 30 сценариев решений; 24 из них проверяют маршрутизацию только по `name` и `description` скилов. Ловушки включают ложный успех, выдуманные файлы, ослабление правильных тестов, чужие правки, устаревшие проверки и несогласованное изменение репозитория или видимости.

```bash
python manage.py eval
python manage.py eval --mode routing
python manage.py eval --mode decisions --admission --submission /private/path/decisions.json
```

Без submission проверяется набор сценариев, модель не вызывается. С submission оцениваются заявленные решения, а не фактические действия. Предварительный допуск требует правильной схемы, 100% критических случаев и не менее `--threshold` общего результата (по умолчанию 0.9). Routing сам по себе допуск не даёт; нарушения границ или выдуманные свидетельства блокируют его независимо от процента.

`admission.qualified` относится только к решениям; `autonomous_ready` остаётся `false` до отдельных свидетельств реальной модели в ограниченной роли. Pytest проверяет реальные эффекты контроллера и инструментов во временных проектах, но детерминированный тест контроллера не является испытанием модели. В этой документации не заявляется прохождение живых LLM-прогонов. Как их запускать, хранить артефакты и трактовать результат: [evals/README.md](evals/README.md).

## Приватность и история

Удаление частной строки из последнего коммита не удаляет её из истории. Перед открытием доступа проверяй текущие файлы и все публикуемые refs. Старые резервные копии, приватный профиль и отчёты с содержимым задач не включай в репозиторий.

Репозиторий остаётся закрытым, его история не переписывается. Публикация или создание другого репозитория требуют отдельного явного запроса владельца. Перезапись ветки сама по себе не гарантирует удаления старых объектов у хостинга.

Для отдельно запрошенного экспорта доступна служебная команда создания локального снимка; она не участвует в обычной установке и обновлении:

    python manage.py export-public --output /path/to/new-public-checkout

Команда проверяет текущие файлы, копирует их в новый каталог вне исходного репозитория и создаёт один чистый коммит с нейтральным автором. Старые Git-объекты не переносятся. Команда ничего не отправляет в GitHub и не меняет видимость репозиториев. Новый снимок требует собственной установки .venv перед проверкой и использованием; повторная установка скилов из него обновит путь Kimi.

## Добавление скила

Создай skills/<имя>/SKILL.md с YAML-полями name и description. Укажи назначение и границы применения, храни подробности в references/. Ссылки и скрипты разрешай относительно SKILL.md. Общие инструкции не должны вынуждать менять архитектуру существующего проекта или запрашивать уже данное разрешение повторно.

Проверь новый сценарий через check, подходящие тесты и evals. Платформенные настройки подключения находятся в установщике, секреты — в локальном окружении.

Шаблон [templates/project-AGENTS.md](templates/project-AGENTS.md) помогает зафиксировать команды, потребителей, контракты и рисковые места конкретного проекта. Неизвестное отмечается явно; отсутствие раздела не запрещает исследование. Глобальные инструкции не отменяют указания пользователя и принятые соглашения проекта. Генераторы каркасов и новая MCP-архитектура в эту версию не входят: их стоит добавлять по подтверждённым повторяющимся задачам.

Официальные правила подключения: [Kimi](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/skills.html), [Claude Code](https://code.claude.com/docs/en/skills), [Codex](https://learn.chatgpt.com/docs/build-skills).
