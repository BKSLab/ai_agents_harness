# Changelog

Формат: [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/). Версия — в pyproject.toml.

## [0.4.0] — 2026-10-05

### Добавлено

- Управляемые задачи `task init/plan/approve/status/verify/snapshot/review`: приватное состояние, контрольные записи после изменений, связь требований и рисков с проверками, fingerprint кода, квитанции контроллера и валидируемые схемы YAML/JSON.
- Режимы `light`, `standard`, `high-risk`, планы совместимости и восстановления для high-risk, сохранение числа итераций ревью и обнаружение отсутствия прогресса. Продолжение и восстановление прерванной проверки без потери состояния.
- Записи точных разрешений `task authorize/check-authorization` и хук Kimi `git_gate`: привязка к действию, репозиторию, remote, ветке и плану; сверка Git index перед коммитом и HEAD перед отправкой, явная цель push.
- `review-gate` с обязательным явно выбранным псевдонимом модели: проверки контроллера на рабочей копии и отдельном снимке, ограниченный reviewer, проверка структуры заключения и актуальности свидетельств. `models` показывает только псевдонимы, без учётных данных; автоматической подмены модели нет.
- Профили Kimi `implementer` и `reviewer` с явными allowlist инструментов, без Bash, делегирования и MCP. Исполнитель читает и правит назначенные файлы, ревьюер читает снимок; команды запускает контроллер.
- Управляемая установка компонентов `skills`, `instructions`, `hooks`, `agents`: объединение TOML, блоки глобальных инструкций с сохранением пользовательского текста, квитанции, обнаружение конфликтов и резервное копирование. Хуки и роли поддержаны для Kimi.
- `capabilities` и расширенный `doctor`: поддержка/наличие/настройка каждой возможности, расхождения и ограниченные синтетические пробы хуков без выполнения переданных shell-команд.
- 30 сценариев заявленных решений и 24 сценария выбора скила только по каталогу. Предварительный допуск модели: строгая схема, все критические случаи, настраиваемый общий порог. Routing и решения отделены от реального выполнения; `autonomous_ready` не объявляется по их результатам.
- Регрессионные проверки контроллера, установки, хуков, схем и оценки решений во временных проектах. Эти тесты не представляются как прохождение реальной моделью полного цикла.

### Изменено

- Процесс соразмеряется с задачей; выбранный пользователем полный цикл сохраняется. Разовое ревью возможно без формального плана, а служебный журнал больше не требует создания `docs/tasks/` в каждом проекте.
- Вердикт ревью использует `approved / changes_requested / blocked`, устойчивые ID замечаний, доказательства, fingerprint, ссылку на план и квитанцию. Ревьюер проверяет результаты контроллера; текст автора не считается подтверждением запуска.
- Глобальные правила разрешают необходимые тесты и документацию, сохраняют уже выданные разрешения и не расширяют их при слове «продолжай». Задача Битрикса сама по себе не разрешает отправку комментария.
- Источник версии унифицирован с pyproject.toml. Обычная установка без `--components` сохраняет совместимость и обновляет только скилы.

### Исправлено

- Длинные пути вложенных снимков на Windows CI: новые рабочие копии хранятся в `HARNESS_HOME/snapshots`, прежние пути остаются действительными. Слишком длинный корень отклоняется до копирования; настройки Git не меняются.
- Маскирование ключей больше не скрывает часть обычного пути `task-<hash>` в диагностике.
- Ложная блокировка `.env.example` и распознавание дополнительных прямых способов чтения/отправки секретных файлов. Хук остаётся ограниченным фильтром, а не песочницей.
- Тихий пропуск Ruff: выбор окружения проекта, явные результаты `passed / failed / skipped / error`, ограниченный вывод и ошибки конфигурации.
- Возможность принять устаревшие проверки или ревью, неподтверждённые поля результата, несовпадающие staged/отправляемые файлы и разрешение для другой цели. Чужие исходные правки требуют изолированного checkout либо явного принятия относящихся к задаче файлов.

### Границы применения

- Роли, записи разрешений и Kimi-хуки работают совместно с контроллером; они не являются OS-песочницей или независимой системой авторизации. Ошибки и таймауты хуков Kimi имеют семантику fail-open.
- Секреты, журнал, снимки и модельные артефакты остаются вне репозитория. Работа продолжается в существующем закрытом репозитории без создания нового и изменения видимости.

## [0.3.0] — 2026-10-05

### Добавлено

- Скил `dev-pipeline`: полный цикл разработки задачи — от ознакомления через риски, план и реализацию до независимого ревью и фиксации. Два гейта пользователя: план и отправка кода.
- Скил `risk-assessment` с чек-листом рисков: контракты, потребители, данные, конкурентность, внешние системы, откат, наблюдаемость, безопасность.
- Скил `code-review` с чек-листом и строгим форматом вердикта (approved + findings с severity и location).
- Шаблон `templates/project-AGENTS.md` для проектов: команды, потребители и контракты, рисковые места.
- Глобальные правила `global/AGENTS.md` (устанавливаются в `~/.agents/AGENTS.md` или аналог инструмента).
- Хуки Kimi Code: `hooks/protect_secrets.py` (барьер на чтение секретов через shell) и `hooks/lint_on_edit.py` (ruff после правки .py), фрагмент конфигурации `config/kimi/hooks.toml`. Подключение ручное, по README.
- Eval-сценарии для трёх новых скилов (всего 18).

## [0.2.0] — 2026-10-05

### Добавлено

- Общий клиент Bitrix (`skills/_shared/`): единый runtime, JSON-контракт, журнал операций SQLite с operation-id.
- Установщик `harness_cli` с квитанциями, откатом и dry-run; `manage.py`: install, doctor, check, eval, operations, export-public.
- Тесты pytest и GitHub Actions на трёх ОС; evals решений модели.
- Раздельные переменные BITRIX_PORTAL_URL / BITRIX_WEBHOOK_USER_ID / BITRIX_WEBHOOK_TOKEN; BITRIX_WEBHOOK объявлен устаревшим.

### Изменено

- Скрипты bitrix-* стали тонкими обёртками над общим runtime.
- README переписан: установка, частная конфигурация, приватность истории.
